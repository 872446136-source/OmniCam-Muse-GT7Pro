# 重构说明（Muse 4.11 GT7Pro）

这一版把"轻量版 / 完整版"两条分支合并成**一个包**，并换掉整套移植思路。下面说清楚改了什么、
为什么改、本机每个功能的真实状态。

产物：https://github.com/872446136-source/OmniCam-Muse-GT7Pro/releases/tag/full
分支：`test/full` ｜ `versionCode 475` ｜ `versionName Muse 4.11 GT7Pro`
目标：真我 GT7 Pro（RMX5010），ColorOS 17.0.0.111，相机 `com.oplus.camera` 17.006.112，相册 `com.coloros.gallery3d` 17.10.37

---

## 1. 上一版为什么黑屏

不是钩子写错了，是**替换了不该替换的东西**。更早的一版 `module/post-mount.sh` 把上游 X9 Ultra 的
`libAlgoInterface.so`、`libBasicTonePhoto.so` 覆盖到本机 `/odm/lib64/`，`post-fs-data.sh` 又覆盖了
`camera_unit_config`、`oplus_camera_config`、决策配置、ISP 调校 bin、gamma 表。

三个致命点：

| 点 | 事实 |
|---|---|
| SoC 不同 | X9 Ultra 是天玑 9500，GT7 Pro 是骁龙 8 Elite。`AlgoProcessData` 这类结构体布局不同，同名库不能互换 |
| 配置格式不同 | 本机 `oplus_camera_preview_decision_config.json`、`oplus_camera_aps_config`、`oplus_camera_algo_switch_config`、`oplus_camera_config` **是加密的**；X9 Ultra（PKU110）这五个全是明文。把明文塞给本机等于喂垃圾 |
| 调校文件不同 | 本机是 `com.qti.tuned.sunny_imx906_main.bin` 这套高通调校，X9 是 `lighthouse*` |

所以相机进程在打开取景器之前就死了 —— 表现为"取景器全黑 + 进相机卡死"。

**这一版的做法：一个系统文件都不换。** 所有功能重建在本机自己的库和文件上。

## 2. 配置加密已经解开了

上一版认定"本机配置加密、改不了，所以 25MP 之类全部没戏"。这一版把封装格式逆出来了：

```
01 01 <4 字节头> <AES-128-ECB 密文> <FF + 3 字节尾>
```

- **Key**：从本机自己的 `libOplusSecurity.so` 偏移 `0x7AB` 起取 32 字节，逐字节 XOR `0x3F`，
  再隔一个字节取一个，得到 16 字节 AES key。
- **头 4 字节 / 尾 4 字节**：原样拷贝。已逐项验证**不是** crc32、不是 adler32、不是 sum，
  解密后重新加密能**逐字节复现**原始文件（round-trip 完全一致）。

工具：`tools/oplus_config.py`（`key` / `dump` / `pack` 三个子命令）。

**这条结论只解决了一半问题**：能解密 ≠ 改了有用。下面第 4 节说清楚哪些真能改出来。

## 3. 架构改动

### 3.1 删掉 Lite

`Profile.java` 整个删除，`installLiteCamera` / `installLiteGallery` 删除，`ModuleEntry` 只有一条路径。

### 3.2 能力探测（`common/Capabilities.java`）

运行时探测本机到底有什么，每个功能按结果决定装不装：

| 探测项 | 含义 |
|---|---|
| `dataLayer()` | 模块的数据层挂上没有（`/odm/etc/camera/meishe_lut` 与父目录不同设备 = 挂上了） |
| `lmt()` | 本机有没有 `/odm/etc/camera/basictone/lmt`（大师色彩 / GR 的宿主目录） |
| `retro()` | 有没有 `basictone/setting_Retro`（POP 必需） |
| `plainDecision()` | 决策配置是不是明文（首字节是 `{`）。X9 是，本机不是 |
| `tuningJson()` | 有没有 `conf_tuning_params.json`（天玑平台才有） |
| `hasMode(name)` | 本机 `camera_unit_config` 的 `mode_type_list` 里有没有这个模式 |
| `profileConfig()` | profile 的 `enabled` 标记在不在（见 3.4） |
| `profileSize()` | 已落地的 profile 字节数，日志里能看出是不是构建出来的那份 |
| `nativeLibrary()` | `libjiege_native.so` 加载成功没有 |

`hasMode()` 先读 profile 里的 `camera_unit_config`，读不到才回落到 `/odm` 原件 —— 这样判断结果
永远是"相机实际会读到什么"，不会因为时序问题误判成"不支持"。

### 3.3 装配注册表（`common/Install.java`）

每个功能一行状态，三种结果：

- `on` —— 装上了
- `off: 原因` —— 本机缺东西，跳过（不影响其它功能）
- `failed: 异常` —— 装的时候抛了，只关掉自己

关键改进：**缺一个输入不再让整个相机功能全灭**。上一版只要 `/odm` 没挂上，`UnmountedGuard` 就把
所有钩子全关；现在纯 Java 功能照常，只有依赖数据的那几个自己跳过。

### 3.4 配置 profile：路径重定向，不挂载

本机 `/odm` 是只读且被 AVB 保护的，往里塞东西要么挂载要么改分区，都是"动系统文件"。
这一版改成**进程内路径重定向**：

```
/odm/etc/camera/config/<name>   →   /data/user/0/com.oplus.camera/files/jiege/profile/<name>
```

- 实现在 `app/src/main/cpp/profile_config.cpp`，`profileRemapPath()` 挂在
  `pop_path_remap.cpp` 的 `remap()` 里，排在 `unlock25mpRemapPath` 之前。
- 只在**相机进程内**生效，别的进程看 `/odm` 还是原样。
- 开关是 `<PROFILE_DIR>/enabled` 这个标记文件；整个目录不存在就完全不走这条路径。

**`/odm` 一个字节都没动。** 卸载模块后不存在"改坏的残留"。

#### profile 由相机进程自己写（440 的关键修正）

430 是让 `service.sh` 用 root 把 profile 拷进相机数据目录，然后跑 `restorecon`。这条路走不通，
实测 `Capabilities` 那行是 `profile=false`，于是移轴 / XPAN 全被跳过、GR 也没有模式入口。两个原因：

1. **`restorecon` 在 app 私有目录上是有害的**。它按 `file_contexts` 重设 context，而那里没有
   per-app 的 SELinux category，于是文件变成 `u:object_r:app_data_file:s0`，app 自己（运行在
   `s0:cXXX,cYYY`）反而读不到 —— 刚写进去就被锁在门外。
2. **开机时 CE 存储可能还没解锁**，root 连写都写不进去，而 `cp ... || true` 把失败吞了。

现在改成 `common/ConfigProfile.java`：相机进程从 **APK 的 `assets/profile/<model>/camera_unit_config`**
读出来，写进自己的 files 目录。进程写自己的目录，owner 和 context 天然正确，而且一定发生在解锁之后。
写临时文件再 rename，避免相机启动时读到半个文件。

配套改动：

- `service.sh` 不再拷 profile，并删掉全部 6 处 `restorecon`（app 私有目录只留 `chown` / `chmod`；
  新文件本来就继承父目录的 category）。唯一保留的 `chcon` 是把目录自己的 context 复制给
  gallery 的 unit SDK jar，那个是对的。
- `customize.sh` 刷入时清一次旧 profile，避免 430 留下的坏文件因为"长度和开头都对"被当成已就位。

## 4. 本机功能状态

实测依据：`dump/omnicam_dump`（本机 `/odm` 与 `/odm/lib64` 的完整导出）、四份配置的解密结果、
以及用户导出的运行日志 `OmniCam-Muse-日志-20261021-142701`。

### 4.1 通过 profile 开启的模式

这四个上一版判定"本机不支持"，**结论是错的**。逐项核对固件后发现，除了 `mode_type_list` 没列之外，
其它东西本机全都有：

| 检查项 | 移轴 `tilt_shift_mode` | XPAN `xpan_mode` | GR `gr_mode` | POP `retro_camera_mode` |
|---|---|---|---|---|
| 操作码 `mode_operation_mode` | 有（`8001`） | 补 `80AC` | 补 `8009` | 补 `8001` |
| APS 算法开关 | 有 | 有 | 不需要（跑在专业模式之上） | 不需要（跑在拍照模式之上） |
| 决策树节点 | 有 `TILT_SHIFT` | 有 `XPAN` | 不需要（`GrModeHooks` 委派给 `ProMode`） | 不需要（复用 `8001` 拍照的树） |
| 输出流数 / usecase | 有 | 补 `xpan_case` | 有 | 有 |
| 渲染数据 | 8000×3636 与裁切区域都在 | 8000×3636 与裁切区域都在 | 跟随专业模式 | `basictone/setting_Retro`，模块已经挂上 |

也就是说：**算法栈本来就在，只是入口没开。**

`gr_mode` 的 operation code `8009` 不是猜的：X8 Ultra（PKU110）现货配置里 `gr_mode` 就等于
`professional_mode` 的值，正好和"GR 跑在专业模式之上"的实现对上。`retro_camera_mode` 同理，PKU110
现货等于 `8001`，也就是拍照模式。

profile 的改动（相对本机原文件，实测 diff）：

- `tilt_shift_mode` → `rear_wide` / `rear_main` / `rear_tele` / `front_main` / `rear_sat`
- `xpan_mode` → `rear_main`；`mode_operation_mode.xpan_mode = 80AC`；`usecase_info.xpan_case`
- `gr_mode` → `rear_wide` / `rear_main` / `rear_tele` / `rear_sat`；`mode_operation_mode.gr_mode = 8009`
- `retro_camera_mode` → `rear_wide` / `rear_main` / `rear_tele` / `rear_sat`；`mode_operation_mode.retro_camera_mode = 8001`
- 相机 override 配置（`service.sh` 写进 `override_config_data.xml`）：
  `com.oplus.feature.xpan.mode.support = 1`、`com.oplus.gr.mode.support = 1`、
  `com.oplus.feature.retro.camera.support = 1`
  —— **这条实际不生效**，见 4.1.2。保留只是因为它无害。

**无重复、无丢失、没有删任何原有模式。** 生成脚本 `tools/make_profile.py`，输入是**本机自己的**
`camera_unit_config`，只做语义插入，不做整体替换。

### 4.1.1 模式栏不在配置里，在数据库里（450 的关键修正）

440 刷完后 `profile=true`、`hasMode("gr_mode")=true`、装配页也显示 GR 已启用，但相机里**就是没有 GR**。
原因不在配置，在相机自己：

- 相机**不**每次启动都从配置重建模式栏，而是把模式写进 `databases/mode_data.db`
  （`ModeDataSQLiteOpenHelper`），之后只查这张表；
- 写表时每一行都过一遍开关：`gr` 要 `com.oplus.gr.mode.support`，
  `retroCamera` 要 `com.oplus.feature.retro.camera.support`；
- 这台机器的表是在装模块**之前**建的，那时开关还是关的，所以 `gr` / `retroCamera` 两行从来没写进去。
  之后无论配置怎么改，表里没有就是没有。

450 的改法：`common/ModeDataReset.java` 在相机主进程里、任何模式代码跑起来之前，把这个 db 文件删一次
（按模块版本号记标记，一个版本只删一次），相机的"db 不存在"分支就会按**当前**开关重新写一遍，
`gr` / `retroCamera` 这时才被写进表里。

- 为什么由相机进程自己删：root shell 往 app 私有目录写会丢掉 SELinux 的 per-app category（440 就是
  栽在 `restorecon` 上），开机未解锁前更是写不进去。
- 代价：用户自己排过的模式顺序会回到默认一次。所以是"一个版本一次"，不是每次启动。

**450 实测：删库成功了，模式还是没出来。** 因为删库只是让相机"重新问一遍"，而问出来的答案还是 false。

### 4.1.2 开关必须由进程回答，不能靠配置补（460 的关键修正）

450 日志里 `ModeData: mode database dropped` 明确出现了，`Install: 23/25`，但模式栏里仍然没有 GR / POP。
顺着写表那条路往上追，才看清开关读的是哪儿：

```
ModeDataSQLiteOpenHelper 写行
  → CameraConfig.getConfigBooleanValue(String)      （符号 CameraConfig.flag）
  → CameraConfig.w(key, false)
  → CameraConfig.b() / y()
  → CameraUnitUtils.getVendorTagConfig(key)          ← 直接读 oplus_camera_config
```

`getVendorTagConfig` 读的是 `oplus_camera_config` **这个文件本身**，不是 override 的 SharedPreferences，
所以 `service.sh` 往 `override_config_data.xml` 里写的那些值在这条路径上根本不会被查。查过本机这个文件
（已解密核对）：

| key | 本机取值 |
|---|---|
| `com.oplus.feature.xpan.mode.support` | `0`（存在） |
| `com.oplus.gr.mode.support` | **不存在** |
| `com.oplus.feature.retro.camera.support` | **不存在** |

缺键 → `w(key, false)` 永远返回 false → 模式行永远不写。`override_config_data.xml`（`CameraConfig.B`）
只在 `b()` 的兜底和 `CameraConfig.u()` 里被碰到，补不出缺的键。

`oplus_camera_config` 是加密的（ColorOS 17：`01 01` + AES-128-ECB + 3 字节尾，头部 4 字节**不是**长度，
实测 `oplus_camera_config` 头 `0101e506`、明文 61749 B），重打包改不动，所以只能在进程内回答。

460 新增 `modes/ModeGates.java`：在相机主进程 hook `CameraConfig.getConfigBooleanValue(String)`，对
`com.oplus.gr.mode.support` / `com.oplus.feature.retro.camera.support` / `com.oplus.feature.xpan.mode.support`
直接返回 `true`；并且**在 hook 装上之前先把原始值读一遍写进日志**：

```
ModeGates: com.oplus.gr.mode.support was false, answering true from now on
ModeGates: com.oplus.feature.retro.camera.support was false, answering true from now on
ModeGates: com.oplus.feature.xpan.mode.support was false, answering true from now on
```

这三行是判断依据：`was false` → 开关确实是那道门；`was true` → 问题在更下游（`pq/h` 的
`position_headline` / `position_mode_panel` 查询，或 `fq/d` 按 rank 去重时把未知模式丢掉）。
（这几行 `was ...` 的日志在 470 里已经删掉了 —— 预读本身就是黑屏的原因，见 4.1.3。现在只有
`answered true` 和 `asked:` 两类。）

`ModeDataReset` 的版本号同步推到 `473`，装完再删一次库，这次播种时开关才真正是 true
（470 那次因为钩子里抛异常，答案根本没设上去，库里的行也就没写出来 —— 见 4.1.4）。

只影响相机进程，不落任何文件。模块关掉，这三个 key 读到的就是固件原值。

**460 的第一版实现是错的，代价是相机黑屏**，见 4.1.3。

### 4.1.3 开关要等应用起来再回答（470 的关键修正）

460 在 `handleLoadPackage` 里做了这件事：

```java
boolean before = (Boolean) getter.invoke(null, key);   // 预读，为了把原始值写进日志
```

`handleLoadPackage` 跑在 `handleBindApplication` 中途，**Application 还没创建**。这时候主动调用
`CameraConfig.getConfigBooleanValue` → `CameraUnitUtils.getVendorTagConfig`，等于把相机的配置引擎提前叫醒：
它在"什么都没有"的状态下把配置读了一遍并缓存下来，相机随后启动，拿到的就是空配置 —— 预览出不来，黑屏。

连带现象：设置页查状态是 `contentResolver.call` 到相机 provider，这个调用**会拉起相机进程并等它起来**；
进程起来就崩，所以永远等不到 → 一直「正在检查」；导出日志走同一条路 → 卡死闪退。

470 的做法（`modes/ModeGates.java`）：

| 规则 | 原因 |
|---|---|
| **绝不主动调用原方法** | 一次预读就够让配置引擎提前初始化 |
| `Class.forName(name, false, loader)` | 加载但不触发静态初始化 |
| 只在 `Application.onCreate` 之后装 hook，外加 `Instrumentation.callApplicationOnCreate` 兜底 | 应用起来后相机自己也会调这个方法，此时调用是安全的 |
| 全程 try/catch，失败只丢功能 | 开关挂了也不能拖累相机启动 |
| `touch /data/adb/omnicam_gates_off` 单独关 | 不用卸模块就能排除这一段 |

`CameraConfig.flag` 也从这个版本的 `symbols.json` 里撤掉了（回到 450 的 **255** 个符号），启动时的符号解析不再碰这个类。

另外 `Diagnostics.kt` 查状态改成独立线程 + 6 秒超时：进程起不来时页面直接说"未被注入"，不再永远转圈。

### 4.1.4 答案要先给，日志要在后（471 的关键修正）

470 的 `ModeGates` 在钩子里多读了一个不存在的参数：

```java
// 470（错的）
String key = (String) param.args[0];
Object fallback = param.args[1];   // getConfigBooleanValue(String) 只有一个参数
```

每次调用都抛 `ArrayIndexOutOfBoundsException: length=1; index=1`。框架把钩子里的异常吞掉、按原方法
继续执行，所以 `param.setResult(TRUE)` **一次都没执行到**。后果链条：

```
钩子抛异常 → setResult 未执行 → 播种时开关读到 false
          → gr / retroCamera 两行没写进 mode_data.db
          → vm/l.i 里 dq/e.q(int) 查不到 → ConditionVariable.block 等满超时
          → 切 GR 卡住；从相册退回相机走同一条查询 → 黑屏卡死
```

日志证据（470）：

```
java.lang.ArrayIndexOutOfBoundsException: length=1; index=1
    at local.jiege.hook.modes.ModeGates$2.beforeHookedMethod(...:47)
    at dq.e.i(DataBaseOperator.java:139)
    at dq.e.h(DataBaseOperator.java:273)
OCAM_ModeSwitcher: checkToSwitchMode, the device is not support the mode:gr
```

异常正好落在 `dq.e.i` / `dq.e.j`（播种模式表的两个方法）写行的地方。

471 的规则：

| 规则 | 原因 |
|---|---|
| 只读 `args[0]`，不碰 `args[1]` | 方法签名就是 `(String)Z`，多读一位必炸 |
| **先 `setResult`，再打日志** | 钩子跑在相机自己的线程上，正在播种模式表；日志出问题不能把答案撤回 |
| 日志包 try/catch | 同上 |
| 记下相机**问过的所有开关名**（`asked:` 前缀，最多 100 条） | POP 还缺，靠这个分辨"压根没问"还是"问了但行被别处丢掉" |
| `ModeDataReset.VERSION = "471"` | 再删一次库，重新播种 |

**这一条是通用教训**：hook 里任何可能抛异常的操作，都不能排在 `setResult` 前面。

### 4.1.5 卡死和"不支持"是同一件事（472）

471 验证通过：`retroCamera` / `gr` / 哈苏水印三个开关都真的回答成 true，POP 入口出来，哈苏水印回来，
`ArrayIndexOutOfBounds` 一次都没有。但 GR / POP 切过去还是卡死。

把切换那条路径从索引里还原出来，`vm/l.i(...)` 只做三件事：

```java
int id = pq.h.f(modeName);                    // 模式名 → 模式 id
AtomicReference r = dq.e.g().q(id);           // 按 id 查 mode_info，阻塞等结果
if (!modeName.equals(row.get().…)) {          // 行名和请求的名字对不上
    Log.e("ModeSwitcher", "checkToSwitchMode, the device is not support the mode:" + modeName);
    return false;
}
```

`dq.e.q(int)`：`ConditionVariable.close()` → 丢给工作线程 → `block(timeout)` → 返回。工作线程
`dq.d.run()` 执行 `select * from mode_info where mode_id = ?`；查不到行 `ref` 就是 null，`block` 等满超时。

**470 的日志里这段只有 3 ms（18.437 → 18.440），所以不是等超时，是查询结果为空。**
而 `CameraControlUI` 在此之前已经打了 `Camera Mode Change Start, next mode: gr` —— 指示器动了，
切换被中途否掉，模式栏就停在半途。**"卡住滑不了"和"不支持"是同一个 bug。**

剩下要分清的是三种可能，从外面看完全一样：行没写进去 / `pq.h.f("gr")` 返回的不是 39 / 行在但字段对不上。
472 不猜了，装只读探针 `modes/ModeProbe.java`：

| 日志 | 含义 |
|---|---|
| `ModeProbe: f(gr) -> 39` | 相机自己把名字转成了哪个 id |

### 4.1.9 B6 移植包：只拿开关，不拿尺寸（475）

`OmniCam-Muse-RMX5010-B6-widescreen`（`Muse 4.4.4-port`，13T 模块底座）在 GT7 Pro 上确实把
哈苏超清、4K live、log 视频、LUT 监看跑起来了。它是怎么做到的：**整套 X9 Ultra 配置**。
`oplus_camera_config` 616 条（本机 519）、`camera_unit_config` 607 行（本机 519）、
`oplus_camera_preview_decision_config.json` 438 KB（本机 227 KB），连
`com.oplus.camera.mode.data.db.version` 都从 5 降到 2。

它的三个 bug 都是同一个原因的不同表现——**尺寸照抄了另一台机器**。

**连拍后相册加载不出来。** B6 改的尺寸：

| 键 | GT7 Pro | B6 |
|---|---|---|
| `high.mfnr.picturesize` | `4000x3008` | `4096x3072` |
| `high.mfnr.tele.picturesize` | `4624x3472` | `4096X3072` |
| `high.mfnr.wide.picturesize` | `4000x3000` | `3264x2448` |
| `sat.wide.support.imagesizes` | `4000x3008…` | `4096x3072…` |
| `sat.ultra.support.imagesizes` | `4000x3000…` | `3264x2448…` |
| `high.livephoto.picturesize` | 不存在 | `4096x3072` |

三点说明这是照抄而不是校准：长焦那行是 `4096X3072`（**大写 X**，同文件其它尺寸都是小写）；
同一组里 `sat.wide` 被放大、`sat.ultra` 被缩小，校准不会出现两个相反方向；`4000x3008` 才是这台
机器 sensor 的 4in1 输出，`4096x3072` 是 8192x6144 的一半，属于 X9U 的 5000 万主摄。
尺寸错 → MFNR 的 buffer 池按错尺寸分配 → 第一张靠缩放糊过去，第二张起 JPEG 头写 4096x3072、
数据是 4000x3008，相册解码失败。

475 **不改任何 `picturesize` / `imagesizes` / `picture.size` / `previewsize`**。
`tools/make_camera_config.py` 里有一条 `FORBIDDEN` 正则兜底，任何尺寸类键都写不进去。

**log/LUT 只能 30 帧。** 两个原因叠加：

1. 本机 `mode_operation_mode.master_video_mode = 80A3`。在 X8U 和 B6 里 `80A3` 是**电影模式**

2. `com.oplus.feature.master.video.60fps.support = 0`，而且
   `com.oplus.video.focus.track.30fps.only = 1` —— 后者更狠：只要开着对焦跟踪（默认开），
   整条录像链路被压到 30，UI 接受 60 的选择然后静默按 30 录。

修法：`master_video_mode → 800b`，新增 `movie_mode: 80A3`（`feature_operation_mode` 走 `80a4` 防抖），
两个开关分别回答 true / false。`800b` 和 `video_mode` 共用一个 op mode 在 OPPO 的配置里是常规做法
（`photo_mode` / `portrait_mode` / `high_definition_mode` / `under_water_mode` 全是 `8001`）。

「哈苏超清开关」和「`highPixel` 进 headline 的条件」——`dq.e.i()` 写 headline 时读它。所以打开它，
页面和入口一起出现，不需要 `ModePlacement` 那种搬移。`high_pixel_mode_featureTable` 本来就在这份
profile 里，一直没用上。

log 页的闸门是 `r9.i`：每个方法都只是 `c(idx, default)`，`idx` 指向

| 槽 | 方法 | 作用 |
|---|---|---|
| 1 | `k()` | 模式闸门（`CameraEntry.l`） |
| 4 | `m()` | log 会话（`qh.e.buildSession` + `LogVideoPresenter`） |

### 4.1.11 POP 的崩溃是「容器在、视图没建」（477）

476 的第一份真机日志里，三次崩溃一模一样，都是 main 线程：

```
NullPointerException: Attempt to invoke virtual method 'void bj.z.l(int)' on a null object reference
  at com.oplus.camera.ui.newsetting.container.t1.run(R8$$SyntheticClass:135)
  at m9.i$a.run(ScheduledRunnable.java:24)
```

离线索引把链条还原成四段：`t1` 是个一次性 runnable（字段 `int a` + `Object b`），`run()` 读
`((gq.t) b).f` 再调 `f.l(a)`；`gq.t` 是 `RetroCameraUIContainer`，`f` 是它的
`RetroCameraUI` 字段；那个字段只在 `gq.t.F9` 里赋值（`bj/z;-><init>` 的唯一调用点）；
`t1.run()` 的字符串是 `showUIInternal` / `showUI, start outer background alpha in`。

**所以不是 POP 画不出来，是 UI 对象没建，延迟的显示动画照样去够它。** `f` 为 null 只有两种
来路：`F9` 没被调用，或者 `F9` 在赋值前就抛了。日志里 `OCAM_*` 全被导出工具过滤掉了，
看不到 `F9` 里那些 `initRetroCamFilterScrollView, root view is null!`，所以两种分不开。

1. 包住 `t1.run()`（符号 `PopUI.show`：`run()V` + `showUIInternal` + `RetroCameraUIAniHelper`），
   原方法照跑、抛了就记一行丢掉。主线程不再被打死，POP 至少能进得去。
2. `RetroCameraUIContainer` 初始化打 `retro UI init start` / `retro UI init done` 两行
   （符号 `PopUI.init`）。**start 有、done 没有 → 初始化自己抛了**，视图缺失就是从这里来的。
3. 被吞掉那一行带上 `retro UI init done: true|false`，一份日志就能定。

两个符号都在旧包上验过（`PopUI.show` → `cp.b.run`，`PopUI.init` → `xq.f0.K9`），不是只对新包
有效的一次性写死。**顺手把 GR 快门的三段边界补齐了**：`shutter message built`（事件消息构造）→
`shutter message dispatched`（进总线）→ `shutter handled by <类>`（哪个模式接住，`hm.i` 是 GR）。
按参数类型找收消息的方法只有三个，不依赖混淆名。

POP 资源那条 `POP PLD resources missing` 也顺手查了：`service.sh` 用的是 `cp -a`，上游数据层
如果用链接组织这些文件，复制到 app 目录里就是一个断链 —— 和"没复制"完全一样。改成 `cp -aL`，
并且资源仍缺失时日志会列出目录里实际有什么（`holds 3: …` / `is absent` / `is a link to …`）。

**为什么这两个特性本机不能用**：GT7 自己那 23 个模式一共用到 **74 个** `com.oplus.*` 特性类。

等于把这些「有代码、从未被使用、一用就炸」的特性全放了进来。

**481 的做法一：重建那张表，只留本机验证过的。** 先算出「本机 23 个模式 + 2 个单元级覆盖
引用到的全部 `com.oplus.*`」——这台机器已经证明能构造的集合——三个新增模式里凡是不在集合里的
条目一律丢弃；`gr_photo` / `retro_camera` / `xpan` 显式保留（它们就是这三个模式存在的理由）；
`super_text` 单独写死剔除；`xpan_mode` **整条不加**（已上架模式，风险最大，等 GR / POP 稳了再说）。

```
gr_mode            entries  64 ->  61, dropped hdr_all_route, scale.focus
retro_camera_mode  entries 232 -> 224, dropped hdr_all_route, super_text, video_live_photo
strings 294 -> 307, modes 23 -> 25, bytes 40091 -> 49621
```

留下的都是本机别的模式正在用的：`gr_mode` 17 个类（`capture_defer`、`capture_params`、
`exposure_time`、`iso`、`focus_exposure`、`time_shutter`、`ten_bit`、`zoom`、`gr_photo` …），
`retro_camera_mode` 39 个类（`retro_camera`、`capture_defer`、`ai_scene`、`beauty`、
`high_resolution`、`live_photo`、`macro`、`qr_code_scanner`、`super_text_two` …）。
`super_text_two` 留着——本机 `photo_mode` 正在用它，能构造，不是崩的那一个。

校验：原 23 个模式解码逐条与改前一致；末尾 5 字节字段原样保留；下标最大 **306 < 307**；
输出可复现（跑两次 md5 都是 `18ca1a7dda9a5832ecff162f6b225d3a`）。

**481 的做法二：`PresenterGuard`。** 表修好了，但「一个 presenter 抛异常就能带走整个进程」
是**相机的**结构性问题，不是表的。以后再加特性，只要有一个构造失败，还是同样的死法。
所以 hook `lc.p.R` —— `BaseFeaturePresenter` 的 stage 分派器，`(int, Bundle, boolean)`，
就是一串 `if (stage == 30000) C1(); else if (30001) N1(b); … else O1(z);`，
POP 崩溃栈里那个 `k2(Z)` 就是它最后一个分支：

```java
XposedBridge.hookMethod(stage, new XC_MethodHook() {
    @Override protected void beforeHookedMethod(MethodHookParam param) {
        try {
            XposedBridge.invokeOriginalMethod(stage, param.thisObject, param.args);
        } catch (Throwable error) {
            Log.i(TAG, "presenter " + param.thisObject.getClass().getName()
                + " threw on stage " + param.args[0]
                + ", swallowed so the mode switch can finish", error);
        }
        param.setResult(null);
    }
});
```

正常返回时行为完全不变（跑的就是原方法）；只有抛异常时被吞掉，那个 presenter 丢掉自己的 init，
模式切换继续走完，日志写清**哪个类、哪个 stage**。481 之后最坏情况是「某个特性不工作」，
而不是「相机整个退出」。逃生口 `omnicam_presenterguard_off`。

注意：这道闸盖的是 `main` 线程的 presenter 路径（POP 那条）。GR 那条走的是
`hb.k0.accept` → `jg.Y`，不经过 `lc.p.R`，所以 GR 的修法**只能是**把 `hdr_all_route` 从表里去掉。

### 4.5 清透 / 琥珀 黑屏：LUT 版本不对

这两个滤镜的 LUT 是 **v4 / 33³**。`.MS-LUT` 的头部结构：

```
0x00 8B  ".MS-LUT "      0x08 ver    0x0C N(每轴采样数)   0x14 通道
0x18    版本常量(1/24/1176)   0x20 头长(48)   0x28 数据偏移 = 48 + N*4
0x30    N 个 float32 轴表, axis[i] = i/(N-1)
data    N³ × 3 字节 RGB
```

本机固件自带的 97 个 LUT 全是 **v1 / 32³**（58 个，98480 B）或 **v3 / 17³**（39 个，14855 B），
**一个 v4 都没有**；而 payload 里恰好只有 `qing_tou.bin` / `hu_po.bin` 是 v4 —— 也恰好就是黑屏的那两个。

`tools/mslut.py` 用三线性重采样把它们转成 v1 / 32³：头部 176 字节直接取自同目录的现货 v1 LUT，
**逐字节一致**；采样误差最大 6/255（网格量化，渲染时还有插值）。CI 在取到上游数据层后自动执行。

`ModeProbe:` 那几行是 472 加的，切一次模式就会多出 `f(...)` 和 `q(...)` 两条，用来定位 GR / POP 卡死：

```
ModeProbe: f(gr) -> 39
ModeProbe: q(39) -> ModeInfo: [mName: gr, mbSupportEdit: true, mPosition: position_headline, ...] (2 ms)
ModeProbe: row gr id=39 position_headline rank=4 front=false edit=true
```

- `f(gr)` 不是 39 → 名字映射错，改映射；
- `f(gr)=39` 但 `q(39)` 是 `null` → 行没写进去，改播种；
- 两个都对但切换仍被否 → 行在，问题在 `vm/l` 后面的分支。

`asked:` 那几行是 471 新加的，用来查 POP：如果列表里**有** `com.oplus.feature.retro.camera.support`，
说明开关确实被问到、答案也是 true，行没写出来就是 `dq/e.j` 里别的条件挡的；如果**没有**，说明相机这一版
压根没走 retro 那条播种分支，要往上找调用方。

看不到模式就看 `logcat -d | grep -i "ModeData\|mode_data"`：删不掉会说 `cannot delete`（权限/路径不对），
删掉了但模式还没出来，把 `logcat` 里 `DataBaseOperator` 那几行发出来即可。

## 8. 出问题怎么回退

按顺序试，每步重启：

1. `touch /data/adb/omnicam_native_off` —— 只关原生层，profile 重定向随之失效，判断是不是原生钩子的问题
2. `touch /data/adb/omnicam_off` —— 整体关掉，相机应回到完全原样
3. KernelSU 里停用模块 —— 连数据层挂载一起撤掉
4. 卸载模块 —— 走 `uninstall.sh`，清干净

因为本版**不替换任何系统文件**，第 2 步之后相机必然是出厂状态，不存在"改坏了要重刷系统"的风险。

## 9. 已知取舍

- **GR 的饱和度 / 对比度 / 清晰度**：上游由原生层写进 LMT 参数，本版原生层在，但这些参数走的是
  `MergeLutTet_resize` 路径，本机没这个符号，所以只有 LUT 生效，数值不生效。
- **快门独立音量档位**：需要挂上游的 `audio_policy_volumes.xml`，本版不换系统音频配置，所以只有
  「静音模式下仍响」生效，独立音量不生效。
- **包体 227 MB**：`master_color/looks` 占 253 MB（未压缩），是大师色彩的成片查找表，属于功能本体。
  不需要大师色彩可以删掉 `payload/master_color` 重新打包，包会降到 ~30 MB。
- **模式顺序会被重置一次**：每个模块版本第一次启动时删掉 `mode_data.db`，相机重新播种模式表，用户自己
  排过的模式顺序 / 首页与面板的分组会回到默认。这是让 GR / POP 出现在相机里的必要代价，每个版本只发生一次。
- **CI 硬性校验**：打包后断言 zip 里**没有** `.so`、**没有** `system/`，APK 里**有**
  `assets/profile/*/camera_unit_config`，一旦不满足直接 fail。这是防止上一版黑屏事故复发的最后一道闸。
